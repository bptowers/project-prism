# Project Prism — Fixes & Status
**Date:** 2026-03-27

## Issues Fixed

### 1. Firestore Batch Write Limit (500 ops/transaction)
**Symptom:** `runWeeklyAnalysis` returned HTTP 500 immediately after `BQ_LIMIT` was raised from 500 → 2,000 records.

**Root cause:** `runAnalysisPipeline` in `functions/src/index.ts` wrote all individual opportunity analyses to Firestore in a single `db.batch()` call. Firestore has a hard limit of 500 operations per batch. At 2,000 records the batch contained 2,000 `set` operations — 4× the limit.

**Fix:** Replaced the single batch with a chunked loop using `FIRESTORE_BATCH_SIZE = 400` (safe buffer below the 500 limit). Each chunk is committed separately before the next chunk starts.

```
// Before: one batch for all 2,000 analyses → FAIL
// After: 5 batches of 400 → OK
```

---

### 2. Firestore Document Size Limit (1 MiB)
**Symptom:** After fix #1, `runWeeklyAnalysis` still failed with:
```
INVALID_ARGUMENT: Document 'reports/2026-03-27' cannot be written because
its size (1,050,156 bytes) exceeds the maximum allowed size of 1,048,576 bytes.
```

**Root cause:** The aggregated report document stored to `reports/{date}` was ~1.001 MiB — just over Firestore's 1 MiB hard cap per document. At 2,000 records, several arrays in the report grow without bound:
- `ThemeCount.examples[]` — one entry per record mentioning each theme
- `CompetitorActivity.contexts[]` — one entry per record mentioning each competitor
- `RegionReport.marketSignals[]` — unbounded market signal strings
- `RegionReport.atRiskDeals[].signals[]` — per-deal signal arrays

**Fix:** Added `trimReportForStorage()` helper in `functions/src/index.ts` that deep-clones the report and caps unbounded arrays before any Firestore write:

| Field | Cap |
|---|---|
| `ThemeCount.examples` | 5 per theme |
| `CompetitorActivity.contexts` | 5 per competitor |
| `marketSignals` / `emergingMarketSignals` | 20 |
| `atRiskDeals` | 50 per region |
| `RiskDeal.signals` | 10 per deal |

Applied at all 6 Firestore write points across `onCSVUpload`, `runWeeklyAnalysis`, and `fetchFromBigQuery` (both base report set and enriched report update in each).

The trim only affects what is persisted — the in-memory report used for Phase 2–5 LLM enrichment is untouched.
