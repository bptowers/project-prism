Project Summary

Project Prism is a Global Revenue Intelligence Engine built for Simpro's sales leadership. It ingests Salesforce opportunity data (via CSV upload or BigQuery), runs each record through LLM analysis, aggregates the results into regional and global reports, then layers on five phases of strategic intelligence — from portfolio analysis to competitive displacement to temporal trend detection.

Live data is flowing into the dashboard with all five enrichment phases completing successfully. The 500 most recent opportunities were analysed and displayed on the dashboard (now increased to 2,000).

The pipeline supports multi-provider LLM analysis (Gemini as primary, Claude and OpenAI available). Data is pulled from BigQuery via Fivetran-synced Salesforce tables, with configurable record limits and automated every-3-day scheduling.

Pipeline Fix #2 — Batch Concurrency
Refactored LLM calls from fire-all to controlled batches of 25 with sequential execution.
Click to expand →
The original Analyzer sent all records to the LLM simultaneously, triggering rate-limit errors (HTTP 429). Refactored to process 25 records per batch with parallel execution within each batch but sequential execution across batches. Added retry logic with exponential backoff (3 attempts, 1-second base delay). This balances throughput against API rate limits while still processing records efficiently.
Session 2
Pipeline Fix #3 — Function Timeout
Increased Cloud Function timeout and memory to handle large datasets.
Click to expand →
Cloud Functions were timing out on datasets with more than ~20 records due to the default 60-second timeout. Increased to 540 seconds (9 minutes) and bumped memory to 1 GiB. Also added the timeoutSeconds: 3600 config on the BigQuery fetch function for larger datasets. These limits are well within Firebase's maximum of 3600 seconds for v2 functions.
Session 2
Pipeline Fix #4 — Two-Phase Enrichment Pattern
Separated base report storage from LLM enrichment to prevent dashboard blanking.
Click to expand →
The original code ran LLM enrichment (executive briefing, recommendations) before storing the report. If enrichment failed, no report was stored at all — causing the dashboard to show sample data. Implemented a two-phase pattern: store the base report immediately with merge:true, then run enrichment as a non-fatal follow-up. The dashboard gets data instantly, and enrichment layers on top when it completes.

Firestore Fix #1 — Batch Write Limit
runWeeklyAnalysis failed with HTTP 500 immediately after BQ_LIMIT hit 2,000. Root cause: single batch.commit() with 2,000 operations — 4× Firestore's 500-op hard limit.
Click to expand →
runAnalysisPipeline in index.ts was writing all individual opportunity analyses to Firestore in a single db.batch() call. Firestore hard limit is 500 operations per transaction. At 2,000 records the batch contained 2,000 set operations — 4× the limit, hence immediate HTTP 500.

Fix: Replaced the single batch with a chunked loop using FIRESTORE_BATCH_SIZE = 400 (safe buffer below 500). Each chunk is committed sequentially. At 2,000 records: 5 batches of 400. Applied across all three Cloud Functions.
27 March 2026
Firestore Fix #2 — Document Size Limit
After fix #1, pipeline failed again: aggregated report at 2,000 records was 1.050 MiB — just over Firestore's 1 MiB hard cap per document.
Click to expand →
Four unbounded arrays in the aggregated report grow linearly with record count: ThemeCount.examples[], CompetitorActivity.contexts[], marketSignals[], and atRiskDeals[].signals[]. At 500 records the document was fine; at 2,000 it hit 1.050 MiB — 2KB over the 1 MiB limit.

Fix: Added trimReportForStorage() helper that deep-clones the report and caps arrays before any Firestore write: examples/contexts capped at 5, market signals at 20, at-risk deals at 50, signals per deal at 10. The in-memory report used for Phase 2–5 LLM enrichment is untouched. Applied at all 6 Firestore write points across the three Cloud Functions.

LLM Prompt Architecture

Project Prism uses a multi-phase LLM intelligence pipeline. The prompts are not summaries — they interrogate the data, applying regional market context, competitor intelligence, and temporal awareness to produce actionable revenue intelligence.

Why do Phases 2–5 run after aggregation?

Phase 1 analyses each opportunity in isolation — it can identify deal-level risks, competitor presence, and sentiment, but it cannot see systemic patterns across the portfolio. Phases 2–5 require the aggregated view: they need to see regional distributions, pipeline coverage ratios, competitive momentum across multiple deals, and forecast-weighted risk. Running them post-aggregation means they operate on the complete intelligence picture rather than fragments. Phase 5 (Delta Intelligence) goes further, comparing the current aggregated report against the previous report to detect trajectory shifts over time.

Intelligence Pipeline Flow
Phase 1 Individual Analysis
Runs: Once per opportunity record (batches of 25, concurrent)
Input: Single Salesforce opportunity record
Output: Win/loss themes, risk signals, competitor mentions, sentiment score, next steps, market signals
Fatal: Yes — pipeline stops if this fails
Prompt philosophy: "This system does not summarise data. It interrogates it. Every prompt is designed to extract intelligence that a human analyst would need 2–3 hours to produce manually."

The prompt embeds Regional Market Intelligence — specific competitor landscapes, buying patterns, and industry dynamics for UK, Australia, New Zealand, and North America. This means the LLM understands that losing to Simpro in AU means something different than losing to Access Coins in the UK.
▼ Aggregation happens here ▼

Individual analyses are combined into regional and global reports. Phases 2–5 operate on this aggregated view.

Phase 2 Portfolio Aggregation
Runs: Once per analysis execution
Input: Full aggregated report (all regions, all metrics)
Output: Executive briefing, strategic recommendations, forecast confidence score, portfolio risk assessment
Fatal: No — base report is saved first, enrichment is a follow-up update
Generates a CRO-ready executive briefing covering pipeline health, forecast confidence (0–100 with methodology), and prioritised recommendations. Designed so Pete Mansel can walk into a board meeting with one paragraph that tells the full story.
Phase 3 Twenty Questions
Runs: Once per analysis execution
Input: Full aggregated report
Output: Answers to 20 strategic CRO questions covering velocity, coverage, conversion, regional performance, competitive dynamics
Fatal: No
A structured intelligence layer that answers the questions Pete would ask in a pipeline review — pipeline velocity trends, stage conversion bottlenecks, win rate by competitor, regional quota coverage, deal age distributions, and forecast risk patterns. Each answer includes evidence and recommended actions.
Phase 4 Competitive Displacement
Runs: Once per analysis execution
Input: Full aggregated report (with competitor data across all deals)
Output: Per-competitor win/loss mechanisms, displacement strategies, defensive playbooks
Fatal: No
Analyses competitive patterns across the entire portfolio — not just "we lost to X" but why and how. Generates displacement strategies for offensive positioning and defensive playbooks for protecting existing pipeline. Requires the aggregated view because competitive momentum only becomes visible across multiple deals.
Phase 5 Delta Intelligence
Runs: Once per analysis execution
Input: Current aggregated report + previous report (fetched from Firestore)
Output: Pipeline trajectory, forecast drift, new/stalled/accelerated deal detection, early warning signals
Fatal: No (gracefully skips if no previous report exists)
The only phase that looks backwards in time. Compares today's report against the most recent previous report to detect what changed — deals that appeared, disappeared, stalled, or accelerated. Identifies forecast drift (is the number moving up or down?) and generates early warnings about pipeline trajectory. This is what turns a point-in-time snapshot into a trend.

Increasing BQ_LIMIT to 2,000 exposed a parser vulnerability: deal notes containing curly brace characters caused the greedy regex to misparse JSON responses. Fixed with responseMimeType: "application/json" (API-level JSON mode) plus a hardened balanced-bracket counting fallback parser. Zero parse failures in runs since the fix.
Resolved Firestore Batch Write Limit — 500 ops/transaction
runWeeklyAnalysis returned HTTP 500 immediately after BQ_LIMIT was raised to 2,000. All 2,000 analyses were being written in a single db.batch().commit() — 4× Firestore's 500-operation hard cap. Fixed 27 March with chunked writes of 400 records per batch (FIRESTORE_BATCH_SIZE = 400). Applied across all three Cloud Functions.
Resolved Firestore Document Size Limit — 1 MiB cap
After the batch fix, the pipeline failed again: the aggregated report document was 1.050 MiB — 2KB over Firestore's 1 MiB hard limit. Four unbounded arrays grow linearly with record count. Fixed 27 March with trimReportForStorage() helper that caps arrays before persistence while leaving the in-memory report (used for Phase 2–5 enrichment) untouched. BQ_LIMIT=2,000 now confirmed stable.
⚠ Deadline Node.js 20 Runtime Upgrade Required
Firebase is deprecating Node.js 20 on Cloud Functions. Deprecation deadline: 30 April 2026. Decommission: 30 October 2026. The upgrade to Node.js 22 is a config-only change in the Firebase functions runtime setting — no pipeline code changes required. Must be completed before 30 April to avoid any service disruption.
